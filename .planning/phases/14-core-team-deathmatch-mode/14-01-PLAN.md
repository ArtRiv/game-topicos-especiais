<objective>
Add server-authoritative team-deathmatch scoring: a new `'team-deathmatch'` MatchMode, a shared per-team kill score, per-player kill/death tracking, a win condition at the configured target, and the two new server->client broadcasts (live team score, final ENDED-with-stats). All protocol changes are mirrored in lockstep between `game-server/src/types.ts` and `src/networking/types.ts`, and the new broadcasts are bridged onto `EVENT_BUS` for downstream scenes. This plan also OWNS the `event-bus.ts` event registry for the whole phase (adds NETWORK_TEAM_SCORE, NETWORK_MATCH_ENDED, and the internal HUD_REVEAL key) so later client plans never edit the registry.

CRITICAL — this plan also performs the single wiring step that makes the entire phase live at runtime: in the `lobby:start` handler the room must be set to the lobby's MatchMode via `room.setMatchMode(lobby.mode)`. The room defaults to `'respawn'` (game-room.ts:32); without this call EVERY `matchMode === 'team-deathmatch'` branch in this phase (scoring/win-check here in Plan 01, spawn/invuln in Plan 02) is dead code and the phase ships a silent no-op.

Purpose: This is the foundation every other Phase 14 plan consumes. The room MatchMode wiring, the score state, the MatchMode union, the broadcast payload shapes, and the bus event keys must exist before the spawn/invuln work (Plan 02), the cinematic UI-reveal (Plan 03), and the HUD plate + results screen (Plan 04) can be built.

Output: The room is correctly set to `'team-deathmatch'` at match start; working server-side TDM scoring + win condition + single win broadcast (TDM-01); a `'team-deathmatch'` MatchMode variant that does not break existing modes (TDM-02); mirrored client protocol types + bus bridges + the phase's event-key registry.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client `spell:hit` claim → server | Untrusted: a client claims its spell hit a target for `damage`. Crosses into the authoritative scoring path. |
| client → server (team identity) | A client could attempt to assert its own team or score. Server must never read team/score from the client. |
| lobby host → server (match mode) | The match mode is taken from the server-side lobby record (`lobby.mode`), not from an arbitrary client message, and applied via `room.setMatchMode`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Tampering / Elevation | server.ts `result.eliminated` scoring branch | mitigate | Kill attribution reads the caster's team ONLY from server-side `#playerInfo` via `addTeamKill(casterId)` / `getTeam(casterId)`; the client never sends team or score. `casterId` is taken from the already-validated `spell:hit` claim that passed `validateHit` (range + freshness + FF). |
| T-14-02 | Spoofing | team-score broadcast | mitigate | `#teamScores` is server-only state; `match:team-score` / `match:ended` are server-emitted broadcasts. Clients render from them and cannot write them. |
