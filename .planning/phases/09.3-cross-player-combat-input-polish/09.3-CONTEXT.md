# Phase 9.3: Cross-Player Combat & Input Polish - Context

**Gathered:** 2026-05-21
**Status:** Ready for planning (after `/gsd-debug` resolves phantom-fireball root cause — see Bug Investigation Strategy below)

<domain>
## Phase Boundary

Make the game playable in multiplayer for the college event. Build the host-authoritative cross-player damage pipeline (PVP-02 / PVP-04 / PVP-05 / PVP-06) that v1.1 was supposed to ship but didn't, add a dash on Shift, rebind the spell-cycle from Ctrl (which closes the browser tab via Ctrl+W) to hold-Spacebar, and fix two known multiplayer desync bugs (earth wall blocks fireball for caster only; phantom 2nd fireball spawned on cast).

**In scope:** damage net protocol + server validator + client application, elimination state with respawn timer, friendly-fire pass-through, dash ability, spell-cycle rebind, both desync bug fixes.

**Out of scope:** new spells (Phase 9.4), combo engine changes (Phase 9.4), kill feed / damage numbers / name tags / HP bars (Phase 12), results screen (Phase 10), spectator camera (Phase 13).

</domain>

<decisions>
## Implementation Decisions

### Damage Authority

- **D-01:** Client-claims, host-validates model (the v1.1 plan recorded in PROJECT.md Key Decisions). Casting client's local physics overlap with a remote player sprite emits `spell:hit { spellId, casterId, targetId, hitPos, spellType }`. Host (`game-server/src/game-room.ts`) checks plausibility against last-known cached player positions and the registered spell's damage value, then broadcasts `damage:confirmed { targetId, amount, spellType, hitPos }` to ALL clients. Clients (including the caster) only apply damage via `LifeComponent.takeDamage()` after receiving `damage:confirmed` — no client-side optimistic damage application (PVP-05).
- **D-02:** Plausibility check details (range tolerance, time tolerance) are tunable constants. Defaults to investigate during research: target within ~2 tiles of `hitPos` AND last position update within ~200 ms. Bad/late claims are silently dropped, no error to client.
- **D-03:** New net types live in `src/networking/types.ts` AND `game-server/src/types.ts` (mirrored, same as `SpellCastPayload`/`SpellCastBroadcast`): `SpellHitPayload`, `DamageConfirmedPayload`, `EliminationPayload`, `RespawnPayload`.
- **D-04:** The earth-wall-vs-fireball desync (caster sees spell stop, observers see it pass through) is solved by the SAME mechanism: when a spell collides with a wall on any client, that client emits `spell:hit-environment { spellId, hitPos }`; host broadcasts `spell:destroyed { spellId, hitPos }` to all clients; every client removes the projectile from its `spellGroup` / `#remoteSpellGroup` on receipt. This piggybacks on the damage pipeline's authority pattern — no second auth mechanism.

### Friendly Fire

- **D-05:** Default OFF (per PVP-06). Same-team projectiles pass through the target — overlap detection is short-circuited at the casting client BEFORE emitting `spell:hit` when caster and target are on the same team. No wasted server roundtrip, no visual hit, no damage number.
- **D-06:** Team detection: the host already knows which players are in which lobby slot via Phase 9 lobby config. Server adds team assignment to the per-player payload sent at match start (already broadcast in some form — researcher to confirm exact path). Client uses received team IDs in the FF pre-check. **If teams are not currently broadcast at match start, the planner adds that as a sub-task** — minimal scope creep.
- **D-07:** A host-toggle for FF in the lobby UI is **deferred to a later phase** (likely 9.4 or 10). For Phase 9.3, FF is hardcoded OFF — same-team hits never register.

### Elimination & Respawn

- **D-08:** Default game mode for Phase 9.3 = **respawn-after-N-seconds**. When a player's HP reaches 0, host broadcasts `EliminationPayload { playerId, eliminatedAt }`. After N seconds the host broadcasts `RespawnPayload { playerId, position }` and the client restores full HP, re-enables input, and repositions the sprite.
- **D-09:** `N` (respawn delay) is a tunable constant — default **5000 ms**. Lives alongside the dash params (see D-13) in `src/common/runtime-config.ts` so all combat tunables share one file.
- **D-10:** Respawn position = the player's original spawn point assigned at match start (matches how `game-room.ts` already allocates slots). No random respawn for now.
- **D-11:** While dead, the dead player's client:
  - Disables input (movement + casting suppressed)
  - Applies a full-screen gray-scale overlay (or color tint — researcher to pick least-invasive Phaser pattern; `cameras.main.setPostPipeline` or a top layer rectangle with alpha)
  - Renders centered BitmapText "RESPAWNING IN N…" that counts down to 0
  - Sprite stays visible at the death location playing death anim (or stays on death frame) until respawn fires
- **D-12:** **Game mode toggle (respawn vs no-respawn)** is structurally supported but not user-exposed in this phase. The respawn code path checks a `MATCH_MODE` config field on the room (default `'respawn'`); switching to `'last-standing'` skips the respawn broadcast and leaves dead players permanently eliminated. The lobby-UI selector for this toggle is **deferred to Phase 9.4 or Phase 10** — leaving "the code spawn after n seconds ready" per user request. ENDED-state win-condition behavior in `'last-standing'` mode is **Phase 10's** responsibility, not 9.3's.

### Dash (Shift)

- **D-13:** Dash params live as named constants in `src/common/runtime-config.ts` so all values can be tuned without source-diving:
  - `DASH_COOLDOWN_MS` (default tbd — researcher to suggest, start ~1500)
  - `DASH_DISTANCE_TILES` (default tbd — start ~3)
  - `DASH_DURATION_MS` (how long the dash motion takes — start ~150)
  - `DASH_IFRAMES_ENABLED` (boolean, default `false`)
  - `DASH_IFRAMES_MS` (number, default `150` — only consulted when enabled)
  - `DASH_CANCELS_CAST` (boolean, default `true` — pressing Shift mid-cast aborts the cast)
  - `DASH_INTERRUPTABLE_BY_CAST` (boolean, default `false` — pressing 1/2/3 mid-dash does NOT cancel the dash by default)
- **D-14:** Dash direction = current WASD movement vector. If no WASD keys are held, fall back to the last-faced direction (already tracked by the animation system via current `*_DOWN`/`*_UP`/`*_SIDE` anim selection).
- **D-15:** Position during dash is broadcast to other clients via the **existing 20 Hz position-update channel** (no new message type). Other clients see the player sprite warp/lerp to dash end position naturally. If the dash visibly judders for observers, an interpolation tweak goes in a follow-up plan.
- **D-16:** **Existing dash animation** — user to verify if one already exists in `PLAYER_ANIMATION_KEYS` (e.g., `DASH_DOWN`, `DASH_UP`, `DASH_SIDE`). If yes, plan uses it. If no, dash visual = a brief afterimage trail or sprite flash (researcher to recommend cheapest Phaser idiom); add "real dash sprite art" to the deferred-ideas list.

### Spell-Cycle Rebind (Ctrl → Hold-Space)

- **D-17:** Pure rebind. The current Ctrl-hold-opens-radial-menu mechanism stays exactly as-is — only the key changes from `Phaser.Input.Keyboard.KeyCodes.CTRL` to `Phaser.Input.Keyboard.KeyCodes.SPACE` in `src/components/input/keyboard-component.ts` (currently line 31, comment at line 34). No threshold, no tap behavior, no menu redesign.
- **D-18:** Space-down opens the radial menu, mouse cursor angle selects the slice, Space-up commits the selection — identical to current Ctrl behavior. Whatever Space was previously bound to in `keyboard-component.ts` (researcher to confirm — likely nothing) must be removed or the binding rebound.
- **D-19:** Ctrl is freed entirely — no longer bound to anything game-related, so Chrome's `Ctrl+W` / `Ctrl+T` / `Ctrl+R` shortcuts pass through to the browser naturally without competing with game input.

### Bug Investigation Strategy

- **D-20:** **Phantom 2nd fireball going straight right** — root cause is unknown and feels like a separate code path firing (stale event listener? pointer-fallback default? double event in one frame?). **Run `/gsd-debug` BEFORE the planning step** so the planner writes a targeted fix task instead of a "diagnose + fix" task with uncertainty. The debug session output (root cause + fix sketch) becomes a referenced artifact when `/gsd-plan-phase 9.3` runs.
- **D-21:** **Earth wall blocks fireball for caster only** — folded into the damage-pipeline plan via D-04. Same `spell:destroyed` broadcast mechanism handles both player hits and environment hits, so this bug auto-resolves when D-01..D-04 land. No standalone fix needed.

### Claude's Discretion

- The exact list of `spell:hit` / `damage:confirmed` / `elimination` / `respawn` field names — match existing naming conventions in `types.ts` (`SpellCastPayload` style).
- Whether the gray-out-while-dead effect is a Phaser post-pipeline, a top-layer rect, or `setTint` on the world camera — pick whatever has the lowest perf impact and least cross-scene coupling.
- Plausibility tolerance constants (D-02) — start with the suggested defaults, leave `// TODO: tune from playtest` markers.
- How the planner splits the work into plans (likely candidates: net types + server validator, client damage application + elimination, dash + input rebinds, wall-destroy broadcast; phantom fireball gets its own plan only if `/gsd-debug` reveals non-trivial scope).

</decisions>

<specifics>
## Specific Ideas

- **Tunable-first philosophy:** the user prefers tweaking via constants over rebuilding, especially for combat feel. Every numeric or boolean lever decided in this discussion lives in `src/common/runtime-config.ts` (or a near-equivalent the codebase already uses). No magic numbers in spell or input components.
- **Game-mode awareness from day one:** even though only `respawn` mode is shipped, the code structure must support a future `last-standing` mode toggle without refactor. This is a structural requirement, not a feature flag for end users.
- **Two desync bugs are MUST-FIX** for the event playtest to be useful — the experience without them is "spells exist but don't reliably do anything," which the user has explicitly said they need to fix.

</specifics>
