# Phase 09.3 Plan 02: Host-Authoritative Damage Pipeline & Net Protocol Summary

Build the complete server-side damage authority and net protocol so Plan 03 can wire the client-side overlap, FF pre-check, and HP application. Adds seven mirrored payload types (`SpellHitPayload`, `DamageConfirmedPayload`, `EliminationPayload`, `RespawnPayload`, `SpellHitEnvironmentPayload`, `SpellDestroyedPayload`, `PosMirrorPayload`), the position-mirror channel that gives the server visibility into player positions (RESEARCH.md §2 critical finding), and the GameRoom validator pipeline (dedupe → FF check → plausibility → cap → broadcast). Three socket handlers added on the server, three sender methods + four inbound event bridges on the client. Pure plumbing — no GameScene wiring, no input changes. Plan 03 depends on this; Plans 01 and 04 are independent.

## What Was Built

### Net protocol (mirrored client/server)

Seven new payload type aliases added to both `src/networking/types.ts` and `game-server/src/types.ts` with identical field shapes, plus the `MatchMode` union (`'respawn' | 'last-standing'`). All payloads documented inline with D-XX decision references.

### Server-authoritative damage state (`game-server/src/game-room.ts`)

Private state added to `GameRoom`:
- `#lastPos: Map<playerId, {x, y, ts}>` — position cache fed by `recordPosition`
- `#hp: Map<playerId, number>` — current HP, decremented by `applyDamage`
- `#confirmedSpellHits: Set<spellId>` — dedupe set for `tryConsumeHit`
- `#respawnHandles: Map<playerId, setTimeout>` — pending respawn timers
- `#playerInfo: Map<playerId, PlayerInfo>` — for `isSameTeam` lookups
- `#matchMode: MatchMode = 'respawn'` — D-12 structural support
- `#spawnPoints: Map<playerId, {x, y}>` — respawn destinations
- `#maxHp: number` — restored on respawn

Public API:
- `recordPosition(playerId, x, y)` — server-time-stamped cache write
- `registerPlayer(info, spawnX, spawnY, maxHp)` — called once per player at match start
- `getSpawnPoint(playerId)` — for respawn broadcast
- `isSameTeam(casterId, targetId)` — D-05 FF check, defensively returns false when either team is undefined
- `validateHit(claim, now)` — D-02 plausibility: same-team check + position cache exists + ts within 200 ms + squared distance within 96² px
- `tryConsumeHit(spellId)` — returns true exactly once per spellId (RESEARCH.md §1 landmine 5)
- `applyDamage(targetId, claimedAmount)` — caps via `MAX_SPELL_DAMAGE` (T-09.3.02-01 mitigation), returns `{newHp, eliminated, cappedAmount}`
- `scheduleRespawn(playerId, onFire)` — skipped when matchMode === 'last-standing' (D-12); restores HP on fire
- `setMatchMode` / `get matchMode` — server-only setter per T-09.3.02-07 mitigation
- `clearCombatState()` — wipes all combat state, cancels pending respawns; called from `removePlayer` (room emptied) and `transitionTo(ENDED)`

Per-player cleanup added to `removePlayer`: on individual disconnect, the player's respawn timer is cancelled and their position/HP/info/spawn entries are dropped so a mid-respawn disconnect doesn't fire a respawn broadcast for an absent player.

### Server socket handlers (`game-server/src/server.ts`)

Three new handlers added next to the existing `game:player-update-mp` relay:

- `game:pos-mirror` — silent no-op if lobby/player not found; calls `room.recordPosition(playerId, x, y)`.
- `spell:hit` — gated on `room.state === 'ACTIVE'`; dedupe → validate → apply → broadcast `damage:confirmed`; on HP-zero, also broadcasts `elimination` and schedules a `respawn` broadcast via `room.scheduleRespawn`.
- `spell:hit-environment` — gated on ACTIVE; dedupe → broadcast `spell:destroyed` to all peers (D-04 wall desync fix).

Player registration with the damage pipeline is now performed inside the COUNTDOWN→ACTIVE transition `setTimeout` in `startCountdown` (the only place that transition happens). Each lobby player is iterated and `room.registerPlayer(info, spawnX, spawnY, 100)` is called with a deterministic per-index spawn offset.

`LobbyManager.getLobbyById(id)` was added as a one-line public helper (Rule 3 — blocking issue; not on the previous API surface but required to iterate players at match start without depending on a socket).

### Client wiring (`src/networking/network-manager.ts`)

- Three sender methods: `sendPosMirror`, `sendSpellHit`, `sendSpellHitEnvironment` — all ride socket.io (NOT WebRTC). The `DcMessage` union is intentionally unchanged because the host is server-side; P2P channels can't carry "host-validated" semantics.
- `startGameTick` now emits `game:pos-mirror` once per 20 Hz tick alongside `sendPlayerUpdate`. Position bandwidth roughly doubles (still negligible: ~4 KB/s/client per RESEARCH.md §2 estimate).
- Four inbound socket listeners added at the end of `#bindSocketEvents`: each bridges its payload directly onto the corresponding `EVENT_BUS` event (`NETWORK_DAMAGE_CONFIRMED`, `NETWORK_ELIMINATION`, `NETWORK_RESPAWN`, `NETWORK_SPELL_DESTROYED`). Plan 03 listens on these in GameScene.

### Tunable constants

`PLAUSIBILITY_RANGE_PX = 96`, `PLAUSIBILITY_STALE_MS = 200`, `RESPAWN_DELAY_MS = 5000`, `MAX_SPELL_DAMAGE = 50` are defined authoritatively in `game-server/src/types.ts` and mirrored client-side in `src/common/config.ts` + `RUNTIME_CONFIG` (debug-panel adjustable). Every constant carries a `TODO: tune from playtest` marker.

### PlayerInfo.team population (D-06)

Plan Task 1 A0 required verifying `PlayerInfo.team` is populated at match-start broadcast. Verification result:

- `team?: number` field is already present on `PlayerInfo` in both `src/networking/types.ts:9` and `game-server/src/types.ts:9` — no re-add needed.
- Population happens via the existing `lobby:assign-team` flow (`LobbyManager.setPlayerTeam`, lobby-manager.ts:91-100). The host assigns teams pre-match; assignments persist on `PlayerInfo` and ride through `lobby:started → matchConfig.players` and out via `match:state-changed`.
- For 1v1 free-for-all where no team assignment happens, `team` stays undefined — `GameRoom.isSameTeam` returns false in that case (defensive `undefined` check), so FF is effectively disabled and 1v1 damage flows normally. This matches D-05/D-07 intent.
- No new code path needed at match start because team data is already on `PlayerInfo` at registration time (via `registerPlayer(info, ...)` in the COUNTDOWN→ACTIVE setTimeout).

## Threat Model Compliance

Mitigations from plan's `<threat_model>` that landed in code:

- **T-09.3.02-01 (Inflated damage claim):** `applyDamage` caps via `Math.min(claimedAmount, MAX_SPELL_DAMAGE)` — confirmed at `game-room.ts` `applyDamage` body.
- **T-09.3.02-07 (Client sets MATCH_MODE via spoofed message):** No client-facing socket setter for match mode exists; `setMatchMode` is a server-internal Room method only. No `socket.on('match:set-mode')` handler.

Documented residual risks (accepted per threat model):
- T-09.3.02-02 (Spoofing casterId for FF bypass): `claim.casterId` is used at face value; full socket→playerId enforcement deferred per CONTEXT.md "cheat-resistance hardening".
- T-09.3.02-03 (Teleport hack): plausibility cache catches stale hits, not perfectly-timed teleports.
- T-09.3.02-04 (Dedupe set unbounded growth): cleared on ENDED; acceptable for ~15-minute matches.
