# Phase 9.3: Cross-Player Combat & Input Polish — Research

**Researched:** 2026-05-21
**Domain:** Phaser 3.87 multiplayer combat plumbing (Arcade physics overlaps, WebRTC reliable broadcasts, input rebinds)
**Confidence:** HIGH (all findings are code-grounded against this repo; no library deltas relied on)

## Summary

Phase 9.3's hard plumbing decisions are already locked in CONTEXT.md; this doc only fills the "how" gaps. The codebase has every primitive needed (a `#remoteSpellGroup` group, mirrored client/server net types, a `RUNTIME_CONFIG` registry, `LifeComponent.takeDamage`, a Direction-from-vector helper, and a working WebRTC reliable/unreliable split) — adding 9.3 is mostly composition. The single design surprise: **the game-server cannot run a position-based plausibility check today because positions never reach it** (they flow peer-to-peer over WebRTC). Section 2 below documents the implication and a minimum-scope workaround.

**Primary recommendation:** mirror the existing `SpellCastPayload` + `network-manager.ts` union-type pattern for the four new message types (`SpellHitPayload`, `DamageConfirmedPayload`, `EliminationPayload`, `RespawnPayload`), but route them over **socket.io reliable** rather than over the WebRTC reliable channel — the host is server-side, so a P2P channel cannot carry "host-validated" semantics. The position cache lives on the server, fed by a tiny new `game:pos-mirror` socket message (5 fields, 20 Hz, piggybacked on the existing tick).

## 1. Cross-player damage overlap pattern

**Finding.** Remote players are tracked in `GameScene.#remotePlayers: Map<string, Player>` (`game-scene.ts:115`), populated lazily in `#onRemotePlayerUpdate` (`game-scene.ts:1639-1664`). They are **not** in a Phaser Group — each is a free-standing `Player` sprite. Their projectiles ARE in a group: `#remoteSpellGroup` (`game-scene.ts:116`, instantiated `:160`). Local spells live in `#player.spellCastingComponent.spellGroup` (`spell-casting-component.ts`).

So the four needed overlaps are:

| # | Overlap | Notes |
|---|---------|-------|
| A | local `player` sprite × `#remoteSpellGroup` | "I was hit by someone else's spell" |
| B | local `spellGroup` × each remote `Player` sprite | "I hit someone with my spell" — caster's authority for emitting `spell:hit` |
| C | `#remoteSpellGroup` × `#earthWallGroup` | Missing today (cause of phantom-fireball symptom #2). One-line addition mirroring `game-scene.ts:845`. |
| D | `#remoteSpellGroup` × `#collisionLayer` | Already exists at `game-scene.ts:845` — no action. |

**Wiring (B) — local spell vs remote player sprites.** Because remote players are a `Map<string, Player>` not a Group, the cleanest Phaser-3 idiom is to register the overlap each time a remote spawns. Add a `#remotePlayerGroup` alongside `#remotePlayers` (mirror `#remoteSpellGroup` style — `this.add.group({ runChildUpdate: false })`) and `#remotePlayerGroup.add(remote)` in the lazy-spawn branch of `#onRemotePlayerUpdate` (`game-scene.ts:1656`). Then a single `physics.add.overlap(this.#player.spellCastingComponent.spellGroup, this.#remotePlayerGroup, callback)` covers all current + future remotes. Group + overlap is significantly cheaper than per-pair overlap registration and is the same pattern the codebase already uses for enemies.

**Wiring (A) — local player sprite vs remote spells.** Single call: `physics.add.overlap(this.#player, this.#remoteSpellGroup, callback)`. Register in `#registerColliders()` next to existing remote-spell colliders at `game-scene.ts:845`.

**Overlap callback shape (caster's, case B).**

```ts
(spellObj, remotePlayerObj) => {
  const remote = remotePlayerObj as Player;
  const spell = spellObj as FireBolt | EarthBolt | IceShard | WindBolt | ThunderStrike | WaterSpike;
  if (!spell.active || !remote.active) return;

  // FF pre-check (D-05). Caster team comes from NetworkManager.matchPlayers.
  const nm = NetworkManager.getInstance();
  const remoteInfo = nm.matchPlayers.find(p => p.id === remotePlayerIdOf(remote));
  const myInfo = nm.matchPlayers.find(p => p.id === nm.localPlayerId);
  if (remoteInfo?.team !== undefined && remoteInfo.team === myInfo?.team) return;

  nm.sendSpellHit({
    spellId: spell.spellId,           // need to expose; see landmine
    casterId: nm.localPlayerId,
    targetId: remoteInfo!.id,
    hitX: remote.x, hitY: remote.y,
    spellType: spell.constructor.name, // or a stable string ID
  });

  spell.explode();  // local visual; non-authoritative
}
```

**Landmines.**

1. **Remote player → playerId reverse lookup.** Remote `Player` instances don't currently carry their `playerId`. The lazy-spawn at `game-scene.ts:1648-1656` constructs them but doesn't tag the playerId on the Player. Easiest fix: store the playerId on the remote (`remote.setData('playerId', payload.playerId)`) at the same site, then read via `remote.getData('playerId')` in the overlap callback. Cheaper than threading a parallel map.
2. **Spell needs a stable spellType string** for the validator and for `damage:confirmed`. `spell.constructor.name` is unsafe under bundler minification. Use the existing `SPELL_ID` constants — every spell already knows its ID via the factory call site. Add a public `get spellId(): string` on the base spell class (one-line change per concrete spell, OR add to a shared parent).
3. **Local caster must NOT apply damage in the overlap callback.** Per D-01/PVP-05 the damage application is deferred until `damage:confirmed` arrives. The overlap callback emits `spell:hit` then `spell.explode()` for visual feedback only.
4. **`spell.explode()` removes from the group automatically** via the existing `Phaser.GameObjects.Events.DESTROY` listener (`game-scene.ts:1767-1769`). No manual cleanup needed.
5. **Each remote player runs the SAME overlap on their end** (their local `#player` overlapping with their `#remoteSpellGroup`). So a single cast → up to N peers each emit a `spell:hit`. Host validator must accept the FIRST plausible claim and silently drop the rest (de-dupe by `spellId`). This is the only place in the validator that needs explicit dedupe logic.

**Code refs.** `game-scene.ts:115-116, 160, 845-858, 864-878, 1639-1664, 1747-1770`. `spell-casting-component.ts:60-93`. `keyboard-component.ts:21-34`.

## 2. Last-known-position cache on game-server (CRITICAL FINDING)

**Finding — design surprise.** CONTEXT.md D-02 says "Host already receives position updates (20 Hz unreliable)". **This is incorrect** under the current code. Position updates flow **peer-to-peer over WebRTC unreliable data channels** (`network-manager.ts:149-162, 421-422`). The `socket.io` `game:player-update-mp` handler at `server.ts:218-227` exists as a stress-test relay but is **not called by any client code** (`grep "game:player-update-mp"` in `src/` returns zero matches). So the server today has zero visibility into player positions and **cannot run a plausibility check based on cached positions**.

**Three options, in order of scope.**

| Option | Mechanism | Pros | Cons |
|--------|-----------|------|------|
| **A. Add a server-bound position mirror** (recommended) | New 20 Hz socket.io message `game:pos-mirror { x, y }` sent from each client in parallel with the existing P2P broadcast | Minimal — ~10 lines server-side, ~5 client-side; preserves WebRTC perf for actual gameplay; gives the validator real data | Doubles position bandwidth (still negligible: 5 numbers × 20 Hz × N players ≈ 4 KB/s/client) |
| **B. Validator without positions** | Server only validates spell type + damage amount + dedupe + rate-limit | No new messages | Defeats half the point of host-authority; teleport hacks pass through |
| **C. Host-client validator (re-host on a client)** | Designate one client as the validator | No server change | Adds complexity, host migration is fragile, defeats `game-room.ts` as authority |

**Recommendation:** **Option A**. Concrete plan:

1. Extend `network-manager.ts` `startGameTick` to ALSO call `this.#socket.emit('game:pos-mirror', { x, y })` each tick. Bandwidth is trivial; reliability via socket.io's TCP is fine since this is for validation, not rendering.
2. Add to `game-room.ts`:
   ```ts
   #lastPos = new Map<string, { x: number; y: number; ts: number }>(); // playerId → snapshot
   recordPosition(playerId: string, x: number, y: number): void {
     this.#lastPos.set(playerId, { x, y, ts: Date.now() });
   }
   validateHit(claim: SpellHitPayload, now: number): boolean {
     const known = this.#lastPos.get(claim.targetId);
     if (!known) return false;
     if (now - known.ts > PLAUSIBILITY_STALE_MS) return false;       // 200 ms default
     const dx = known.x - claim.hitX, dy = known.y - claim.hitY;
     return dx*dx + dy*dy <= PLAUSIBILITY_RANGE_PX * PLAUSIBILITY_RANGE_PX;
   }
   ```
3. Add `server.ts` handler: `socket.on('game:pos-mirror', ({ x, y }) => { const pid = room.getPlayerIdBySocketId(socket.id); if (pid) room.recordPosition(pid, x, y); });`
4. Add `socket.on('spell:hit', …)` calling `room.validateHit` and, on success, `io.to(lobby:${id}).emit('damage:confirmed', …)`. Also dedupe by `spellId` (a `#confirmedSpellHits = new Set<string>()` cleared on transition out of ACTIVE).

**Defaults to seed.** `PLAUSIBILITY_RANGE_PX = 96` (~2 tiles at 32 px tilesize) and `PLAUSIBILITY_STALE_MS = 200`. Mark both `// TODO: tune from playtest`.

**Landmines.**

- Don't put `#lastPos` outside `GameRoom` — it must clear when the room ends (`removePlayer` already clears `#loadedSocketIds` at line 29; add `#lastPos.delete(playerId)` there).
- Spell-type → damage-amount mapping: the server must know each spell's damage to put it in `DamageConfirmedPayload.amount`. Option (i) replicate the damage table in `game-server/src/types.ts` — simple, drifts over time; option (ii) ship the claimed damage in `SpellHitPayload.damage` and cap-check it server-side against a max table. Option (ii) is cheaper to maintain; cap table can be a single `MAX_SPELL_DAMAGE = 50` constant for v1.
- Server clock vs client clock: position timestamps are server-side (`Date.now()` in `recordPosition`), and the hit-receipt timestamp is also server-side. No clock-sync issue. Don't accept client `ts`.

## 3. Dash motion in Phaser 3 Arcade physics

**Finding.** Three Phaser 3 options exist:

| Approach | Code | Pros | Cons |
|----------|------|------|------|
| Instantaneous `setVelocity` boost over a Phaser timer | `body.setVelocity(vx, vy)`; `time.delayedCall(DASH_DURATION_MS, () => body.setVelocity(0, 0))` | Cheapest; physics handles collisions natively (no tunneling at sane velocities) | Player keeps colliding with the world — desirable for a dash that respects walls |
| Tween on `body.x/body.y` | `this.tweens.add({ targets: body, x: targetX, y: targetY, duration: DASH_DURATION_MS })` | Smoothest visual | Bypasses physics collision response; can tunnel through walls; risk of getting stuck inside walls |
| `setPosition` jump | `player.setPosition(targetX, targetY)` | Trivial | No visual motion; bypasses collisions entirely |

**Recommendation: velocity boost (option 1).** With DASH_DISTANCE_TILES=3 (96 px) and DASH_DURATION_MS=150, the dash velocity is 96/0.15 = 640 px/s. Arcade physics CCD handles this fine — the existing `FIRE_BOLT_SPEED` is in the same ballpark and doesn't tunnel walls. **Tunneling threshold is roughly `body_size / fixedStep ≈ 16 / (1/60) = 960 px/s`** — 640 leaves margin.

**Direction derivation.** Mirror the existing pattern from `spell-casting-component.ts:63-73`: compute `(dx, dy)` from input. For dash, `(dx, dy)` is the WASD vector:

```ts
let dx = 0, dy = 0;
if (controls.isLeftDown) dx -= 1;
if (controls.isRightDown) dx += 1;
if (controls.isUpDown) dy -= 1;
if (controls.isDownDown) dy += 1;

if (dx === 0 && dy === 0) {
  // Fallback to last-faced direction. Player.direction holds the 4-way; convert to vector.
  const d = player.direction;
  if (d === DIRECTION.LEFT) dx = -1;
  else if (d === DIRECTION.RIGHT) dx = 1;
  else if (d === DIRECTION.UP) dy = -1;
  else dy = 1;
}

const len = Math.hypot(dx, dy);
const speed = DASH_DISTANCE_TILES * TILE_SIZE / (DASH_DURATION_MS / 1000);
body.setVelocity(dx / len * speed, dy / len * speed);
this.time.delayedCall(DASH_DURATION_MS, () => body.setVelocity(0, 0));
```

**Cooldown enforcement.** Track `#lastDashTime` on the Player and refuse new dashes until `scene.time.now - #lastDashTime >= DASH_COOLDOWN_MS`. Same pattern as `spell-casting-component.ts:#lastCastTime`.

**Cast-cancel and cast-interrupt semantics (D-13).** `DASH_CANCELS_CAST = true`: if the player is in `CASTING_STATE`, transition back to `IDLE_STATE` before applying dash velocity (state-machine has a `setState` method already). `DASH_INTERRUPTABLE_BY_CAST = false`: the cast handler in `spell-casting-component.ts:42` (check around there for the early-return guard) needs `if (player.isDashing) return;` — track via a boolean flag on Player set true during the dash window.

**Remote sync (D-15).** Nothing to do. The existing 20 Hz `sendPlayerUpdate` (called from `startGameTick`) reads `this.#player.x/y` directly — when the dash moves the player, the next tick's snapshot reflects it. The receiver-side interpolator at `game-scene.ts:1666-1704` lerps to the new position over ~50 ms (`lerpSpeed = 20`). Total perceived dash duration on observers ≈ 150 ms motion + 50 ms lerp = 200 ms, acceptable for v1. Note in deferred ideas: if dash visibly judders for observers, a dedicated dash-broadcast event can be added later.

**Landmines.**

- The `Player` is a `CharacterGameObject` that has its own state machine. The dash velocity will be overwritten next frame if `MoveState.update` runs and calls `body.setVelocity` from WASD input. Solution: either (a) set `isMovementLocked = true` for `DASH_DURATION_MS` so MoveState skips its velocity update — mirror the existing fire-breath pattern in `game-scene.ts:237`, OR (b) add a `DASH_STATE` to the state machine. **Recommendation: (a)** — much smaller surface area, consistent with existing in-cast lock.
- Don't add the dash via the state machine queue dispatch — E10 in the debug doc shows the queue dispatch is buggy (`args` not spread). Either fix that bug as part of this phase (it's two characters of code) or invoke the dash directly. Recommendation: fix E10 in the same change-set as the input rebind plan — it's already on the radar.

**Code refs.** `keyboard-component.ts:21-34, 105-107`. `input-component.ts:158-164`. `spell-casting-component.ts:60-73`. `game-scene.ts:1666-1704`. `state-machine.ts:44` (E10 bug).

## 4. Gray-out-while-dead visual

**Finding.** Three candidates in CONTEXT.md D-11. Survey of current codebase usage:

- **`setTint` on individual sprites** — used everywhere (`game-scene.ts`, `loading-scene.ts`, `main-menu-scene.ts`, spells). Cheap, no plumbing.
- **`cameras.main.setBackgroundColor`** — used in `loading-scene.ts:106`. Available but tints only the gap pixels, not the world.
- **Post-pipeline (`setPostPipeline`)** — used once in `drow.ts:102` (`this.postFX.addWipe(...)`) as a per-sprite postFX, NOT as a camera-wide grayscale. No camera-level post-pipeline is currently registered anywhere in the codebase.
- **Top-layer rect with alpha** — not currently used.

**Recommendation: top-layer dark rect + a gray tint on the dead player's sprite.**

```ts
// On EliminationPayload receive for local player:
const overlay = this.add.rectangle(0, 0, this.scale.width, this.scale.height, 0x222233, 0.55)
  .setOrigin(0, 0).setScrollFactor(0).setDepth(9999);
this.#player.setTint(0x666666);                 // tint corpse gray
this.#deathOverlay = overlay;
// Plus the BitmapText countdown — see below.

// On RespawnPayload receive:
this.#deathOverlay?.destroy(); this.#deathOverlay = undefined;
this.#player.clearTint();
this.#player.setPosition(spawnX, spawnY);
this.#player.lifeComponent.heal(maxLife);       // need to add heal() to LifeComponent — one-liner
```

**Why over a post-pipeline:** zero plugin registration; works in 5 lines; matches the existing codebase's tinting/overlay vocabulary. A real grayscale pipeline would require registering a custom `Phaser.Renderer.WebGL.Pipelines.PostFXPipeline` subclass with a fragment shader — significant scope for a phase that ships placeholders. **Note: A genuine "grayscale" tint requires a luminance-preserving shader; flat-color overlay is "darken + neutral tint", not luminance grayscale. This is the documented limitation and is acceptable per CONTEXT.md "least-invasive" criterion.**

**Countdown text.** BitmapText per `09.2-CONTEXT.md` requirement. Centered on screen, `setScrollFactor(0)`, depth above the overlay. Update text in a `time.addEvent({ loop: true, delay: 1000 })` started on EliminationPayload, killed on RespawnPayload.

**Landmines.**

- `setTint(0x666666)` will not look gray on a sprite that already has a team tint. For 9.3 it's acceptable to just stack — the overlay dims everything anyway. Document as a known minor cosmetic.
- The overlay AND countdown text live in `GameScene`, not `UIScene`. Reason: the death event is per-player gameplay state, and `UIScene` would need an event bridge. Adding them in `GameScene` keeps cross-scene coupling at zero. Watch `#combatLocked`-style lifecycle: the overlay must be cleared on scene shutdown (`Phaser.Scenes.Events.SHUTDOWN`).

**Code refs.** `loading-scene.ts:106`. `drow.ts:102`. `player.ts:97` (existing `setTint` usage for team color).

## 5. i-frames pattern (when `DASH_IFRAMES_ENABLED=true`)

**Finding.** The damage application is gated entirely on receipt of `damage:confirmed` (D-01). So i-frames need to short-circuit ONLY the application step, not the server roundtrip — the host already broadcast the damage; the dashing client just ignores it.

**Recommendation: boolean flag + timestamp on Player.**

```ts
// In Player:
public iFrameUntil: number = 0;

// On dash start, IF DASH_IFRAMES_ENABLED:
this.#player.iFrameUntil = this.time.now + RUNTIME_CONFIG.DASH_IFRAMES_MS;

// In the damage:confirmed handler, when applying to local player:
if (payload.targetId === nm.localPlayerId && this.time.now < this.#player.iFrameUntil) {
  // Drop the damage silently. Player visually un-hurt; HP unchanged.
  return;
}
this.#player.lifeComponent.takeDamage(payload.amount);
```

**Why not a physics layer swap?** Phaser 3 Arcade does not have per-body collision masks; you would have to disable/enable the body (`body.enable = false/true`) or move to a different group. Both interact badly with the existing colliders against walls — you'd phase through the world during the dash. The boolean-flag approach is the cleanest and matches the "gate the consumer, not the producer" pattern already used throughout this codebase.

**Code refs.** `life-component.ts:22-30` (no changes needed).

## Common Pitfalls (3-5 most likely failure modes)

1. **Forgetting to dedupe `spell:hit` on the server.** N clients each detect the same overlap (their own copy of the spell hitting their own copy of the remote player) and emit. Without dedupe by `spellId`, the target takes damage N times. Mitigation: `#confirmedSpellHits = new Set<string>()` checked before broadcasting `damage:confirmed`.
2. **Not assigning playerId onto the remote `Player` instance.** The overlap callback receives the sprite, not its ID. Add `remote.setData('playerId', payload.playerId)` at spawn time (`game-scene.ts:1656`). If skipped, the validator gets `undefined` targets.
3. **Position mirror sent too aggressively.** Reusing the existing 20 Hz tick is fine; do NOT emit on every `body.position` change — socket.io reliable is TCP-backed and will buffer.
4. **`isMovementLocked` not cleared at dash end.** If the `delayedCall` doesn't fire (scene shutdown, player death mid-dash), the player is stuck. Always wrap the timeout in `try/finally` semantics — or better, set `isMovementLocked = false` unconditionally in the death/respawn handlers.
5. **Phantom-fireball fix not testing the secondary collider gap.** The debug doc's fix #1 (null-guard) prevents NEW phantoms, but fix #2 (add `#remoteSpellGroup` vs `#earthWallGroup` collider) is what makes legitimate remote fireballs respect walls — without it the earth-wall-blocks-fireball desync (D-21) remains. **Both fixes must ship.**

## Suggested Plan Splits

My read on a clean 4-plan split (the planner is free to override):

1. **Plan A — Phantom fireball + wall-vs-remote-spell + state-machine queue bug.** Tactical, isolated, no net protocol changes. Three small fixes in `game-scene.ts:1760-1761`, a one-line collider mirror near `:845`, and the E10 `...args` spread in `state-machine.ts:44`. Ships independently and improves the v1.2 playtest experience immediately. Verification is trivial (2-client repro).
2. **Plan B — Damage net protocol + server validator + position mirror.** All the new net types (`SpellHitPayload`, `DamageConfirmedPayload`, `EliminationPayload`, `RespawnPayload`) mirrored in both type files, new socket events (`spell:hit`, `damage:confirmed`, `elimination`, `respawn`, `game:pos-mirror`, `spell:hit-environment`, `spell:destroyed`), `GameRoom` extensions (`#lastPos`, `recordPosition`, `validateHit`, dedupe `Set`, respawn `setTimeout` mirroring `#countdownHandles`), `network-manager.ts` sender methods + dispatcher cases. Pure plumbing — no game-scene wiring yet.
